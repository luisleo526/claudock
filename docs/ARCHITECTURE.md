# Architecture

Claudock is a Swift package with a macOS menu bar executable (`ClaudockApp`), a bundled CLI (`claudock`), and a separately testable core. Both executables use the same registry and launch validation. Its primary interface is a SwiftUI view inside a transient AppKit `NSPopover`, anchored to an `NSStatusItem`. Clicking outside dismisses the popover. An explicit window action opens the same dashboard in an ordinary closable, minimizable, resizable `NSWindow`. The app bundle uses `LSUIElement` so it behaves as a menu bar utility without a permanent Dock icon.

## Components

| Component | Responsibility |
| --- | --- |
| `ProfileDiscovery` | Read bounded zsh startup files and literal includes; recognize `claude-*` aliases/functions and bind them to literal config directories. |
| `ProfileStore` / `ProfileManager` | Own the registry, import bounded shell discovery on first use or explicit rescan, and mutate profile names/bindings while preserving Claude data and shell files. |
| `ShellIntegration` | Opt in to a namespaced CLI command and missing profile shortcuts, upgrade unchanged owned integration files, and synchronize only owned functions through zsh hooks. |
| `ClaudockCLI` | Validate command arguments before I/O, expose registry CRUD, quota, and Console credit, and launch Claude with direct `execve` in the current working directory (Console profiles: as a supervised child; endpoint profiles: with the endpoint's environment). |
| `CredentialStore` | Read the exact profile credential, preserve its complete JSON, and conditionally update the existing Keychain item or credential file. |
| `APIKeyStore` / `ConsoleAPIKey` | Parse Console API keys as data, keep them in a separate Keychain namespace, and read them only to launch their profile. |
| `EndpointConfiguration` / `EndpointAPIKey` / `EndpointKeyStore` / `EndpointLaunch` | Validate a third-party endpoint's URL, pinned model, and catalog mapping, parse its key as data in a Keychain namespace of its own, and build its launch environment, per-launch `--settings` object, and argument checks. |
| `EndpointSession` / `ClaudeCommandLine` | Read Claude Code arguments as its parser does, resolve the session `--continue` or `--resume` would load, and report the other models that replied in it. |
| `ConsoleLogin` | Check, from attributes only, that Claude Code's own Console sign-in keeps an API key for a profile, and read the Console organization's name as display text. |
| `ProfileKeychainItems` | Name the Keychain items a profile can leave behind, look up which exist from attributes only, and build the `security delete-generic-password` command a person can run. |
| `APICreditLaunch` / `APICreditReceiver` / `APICreditStore` | Run a Console profile's Claude as a child that reports each request's cost to a loopback OTLP receiver, and keep the Console credit ledger. |
| `CredentialRefresher` / `ClaudeCredentialLock` | Renew expired or rejected access tokens with shared Claude locks, scoped OAuth requests, conditional persistence, and bounded retries. |
| `UsageClient` | Fetch the HTTPS usage endpoint with an ephemeral session, no redirects, timeouts, and status-specific errors. |
| `UsageCache` / `UsageFetcher` / `UsageRow` | Keep each subscription profile's last reading and HTTP 429 cooldown in a private file shared by the app and CLI, let one process at a time request quota, half a second apart, under a fetch lock, and decide what a dashboard row shows from the cache and each result. |
| `UsageSnapshot` | Decode supported usage-response shapes into displayable windows and reset dates. |
| `SessionAnalytics` | Scan bounded local session logs, deduplicate message usage, and aggregate recorded tokens by day and profile. |
| `MonitorStore` | Coordinate discovery, sequential polling through `UsageFetcher`, per-account state, cooldowns, and preferences on the main actor. |
| `MonitorView` | Render account limits, stale states, settings, and profile actions. |
| `OverviewView` / `SessionsView` | Show local activity and searchable sessions; collect an explicit target profile before a continuation. |
| `TerminalLauncher` / `LaunchCommand` / `ClaudeExecutable` | Resolve the shared executable preference, isolate the profile environment, and quote arguments for GUI Terminal launches; CLI reuses environment validation with direct argument vectors. |
| `WelcomeView` | Introduce the app, detect Claude, and route new users to add/import profiles. |
| `AppDelegate` | Own the menu bar item, transient popover, optional ordinary dashboard window, and application lifecycle. |

## Refresh flow

1. Load the app-owned profile registry. On first use, import active statically discovered shell profiles, including sourced legacy wrappers; later shell rescans are explicit.
2. Reuse the prior state only when the profile binding still matches.
3. Show each account's cached reading and running cooldown from the [usage cache](#usage-cache-and-request-pacing), which `claudock usage` also writes; at launch they appear before any request.
4. Skip profiles whose rate-limit cooldown has not elapsed and, on an automatic refresh, profiles that any Claudock process read within half the refresh interval.
5. For each remaining profile, take the shared fetch lock, read credentials, and make its request, at least 500 ms after the previous request of any process. Discovery, credential I/O, and the lock wait run off the UI thread.
6. Save and show the successful reading, or retain the previous one with an explicit stale/error state; HTTP 429 records a cooldown in the cache.
7. After the account pass, release the fetch lock and schedule the next automatic check using the selected 1-, 5-, or 15-minute interval. Manual refresh asks again for every profile that is not cooling down and has a separate one-minute cooldown.

The monitor needs no background web service, database, or credential synchronization. Usage readings are in memory and in the usage cache. Dismissing the popover or closing the dashboard leaves polling active until the menu bar app quits. Polling resumes after sleep when the next check is due.

## Local analytics

`SessionAnalytics` reads main JSONL sessions, direct subagent logs, and recognized workflow logs under `<project>/<sessionUUID>/subagents/workflows/wf_*/` for a selected 7- or 30-day window. It resolves the selected config and `projects` roots, including symlinked roots, while rejecting symlinked descendants/files. New profiles share the default `~/.claude` history through symlinks. Multiple profiles that resolve to the same history root share one scan and contribute to the `shared-history` bucket, displayed as **Shared history**. CLI logs do not provide a reliable account identity, so shared-root totals remain unattributed to individual accounts. Per-profile totals require isolated history folders, such as an imported directory with its own history.

File enumeration, line length, file size, cumulative bytes, message count, and elapsed time are bounded; incomplete or invalid input produces a partial-history flag. The background scan allows 120 seconds, 8 GiB total, 512 MiB per file, 32 MiB per line, 50,000 files, 400,000 directory entries, and 250,000 unique message records. `eligibleFiles`, `scannedFiles`, and `scannedBytes` provide coverage alongside the partial flag; equal file counts do not imply all records were valid.

For assistant records with usable usage counters, the scanner adds input, output, cache-read, and cache-creation tokens. Duplicate records are keyed globally across main, subagent, copied, and forked logs by message ID, falling back to request or record ID. Repeated snapshots of an identified message merge counter maxima. Across isolated histories, duplicated history is attributed to the oldest local file copy; shared roots retain shared attribution. This heuristic prevents duplicated transcripts from adding the same message twice; it does not establish account billing ownership. Missing identifiers or malformed counters make the scan partial.

Calendar-day chart buckets use the Mac's current calendar. Reused context across distinct requests remains part of each request's recorded token totals. The headline is processed tokens including cache counters; input plus output is shown separately. `subagentTokens` identifies an included subset, not an additional amount to add to the total. Neither the aggregate nor per-profile figures are subscription quota, billed cost, or unique text. The Overview cache reuse ratio is cache-read tokens divided by input plus cache-read plus cache-creation tokens.

Analytics runs off the UI thread. A generation number prevents an earlier scan from replacing a newer requested period. Summaries remain in memory. The scanner extracts usage, local project paths, timestamps, and session identifiers for the UI; transcripts and analytics are not uploaded by this app.

## Session continuation

The Sessions tab shares the analytics period and lists up to 100 recent search matches. A user explicitly chooses a target profile for **Continue as…**. The app verifies the source remains a regular, non-symlink JSONL file and that the project directory exists, then launches the selected Claude executable with the absolute source path as `--resume` and `--fork-session`.

The launcher clears conflicting provider, credential, model, and nested-session environment variables and supplies the target config directory. It writes a private temporary `.command` file and opens it with Terminal through `NSWorkspace`; the script deletes itself before executing Claude. It does not stop the original process or move the source transcript. Claude owns fork persistence, authentication, project trust, and tool permissions. Absolute-JSONL resume argument support was checked against Claude Code 2.1.263; source inspection or launch alone does not establish a completed live continuation.

## Preferences and onboarding

The three-step welcome sheet explains limits versus local activity, detects Claude, offers account setup, and explains how to open and dismiss the menu bar popover. Users can select a custom executable if discovery misses it. `UserDefaults` stores appearance, accent, compact layout, email visibility, usage sorting, refresh interval, executable path, the inference-token requirement, and onboarding completion. Available appearances are System, Light, and Dark; accents are Copper, Sage, Iris, and Blue. The app delegates optional launch-at-login registration to `SMAppService`.

`--demo` opens the ordinary dashboard window with synthetic profiles and readings, without account discovery, Keychain access, history scanning, or usage HTTP requests. A visible DEMO label identifies it, and profile mutations and session launches are disabled. It supports public screenshots and UI checks without personal data. Appearance controls still use local preferences; demo rendering is not evidence of live service or authentication behavior.

`--analytics` performs a read-only local scan and prints token categories and coverage. `--through` supplies an ISO 8601 upper timestamp; the diagnostic's lower bound remains the start of the current seven-calendar-day window. It does not read credentials or call the usage endpoint, and it does not freeze files while Claude writes them. Diagnostic output can include profile names and usage patterns and is not a public fixture.

## Profile and authentication identity

`~/Library/Application Support/Claudock/profiles.json` is the authoritative profile registry for both executables. Reads, which serve launches, listings, usage, and the dashboard, share its lock, so parallel launches never wait for one another; a read that finds the registry missing or a migration pending writes it under the exclusive lock instead. Changes take the lock exclusively. Either side waits up to five seconds for the other before reporting that another profile update is in progress. Profile records have stable registry identities, friendly names/commands, and exact Claude config-directory bindings. New account directories use `accounts/<stable-id>/claude/`; a rename changes the label without changing its config directory or path-derived Keychain service. Imported directories are never moved. The default profile retains Claude Code's default credential service. Credential lookup must never cross to a different profile when an entry is missing or unavailable.

New profiles retain a private UUID config root for independent authentication, while symlinks share projects/history and common settings, plugins, and skills from `~/.claude`. Credential identity remains bound to the private config path; sharing history does not merge logins. Shared settings changes apply to the profiles using those links. Explicit folder imports retain their existing layout and do not receive automatic shared-data links.

Initial import statically reads active shell declarations, including the prior `~/.config/claude-usage/profiles.zsh` only when sourced. Orphaned legacy JSON registries are preserved but not automatically imported. Those legacy files and source lines remain intact. Later polling loads the registry rather than reinterpreting startup files; a deliberate shell-import action refreshes external declarations. Profile add, rename, and removal operate on the registry and do not write `.zshrc`. Removal preserves the Claude config directory, conversations, credential entries, and external shell wrappers; [the credentials it leaves](#credentials-a-removed-profile-leaves) are listed for the person removing the profile.

Shell integration is a separate, optional mutation. It writes `~/.config/claudock/init.zsh` and a marked loader block in `.zshrc`, taking an exact backup before modifying an existing shell file. Version 4 exposes the `claudock` function bound to the installed app's bundled executable and creates missing `claude-NAME` shortcut functions. Existing user aliases, functions, and executables take priority; the default `claude` command is preserved.

Shortcut synchronization runs at source time and through zsh `precmd` and `preexec` hooks. `preexec` covers a GUI profile addition made while the shell is already sitting at a prompt, before that user's next entered command executes. The internal `claudock shell profile-names` emitter reads an existing registry snapshot as data without discovery, registry creation/writes, profile locking, credential access, or networking. Generated shortcuts forward the full selector through `claudock run`, preserving argument boundaries. Rename/removal cleanup only removes functions whose current bodies exactly match the definitions Claudock recorded; externally changed definitions remain intact. Profile CRUD continues to update only the registry and never rewrites `.zshrc`.

The app upgrades an already-enabled, unchanged owned v1–v3 integration to v4 on startup. All three legacy renderers retain their exact output for ownership validation. It does not enable integration when off, and upgrade failures appear in Manage profiles. An existing Terminal session must source `~/.config/claudock/init.zsh` once or open a new tab to install the new hooks. Subsequent profile changes use those loaded hooks and require no further reload. Disabling integration removes the owned startup files/block; open a new shell to unload previously installed functions and hooks. Re-enable integration after moving the app to update the bundled executable path.

The app and CLI use the same custom executable preference domain. The bundle identifier remains `io.github.claudeusage.ClaudeUsage` during the Claudock branding migration to preserve existing preferences and login-item identity. Branding does not move account directories or alter credential bindings.

`claudock run NAME -- ARGUMENTS`, `claudock profile login NAME`, and `claudock profile setup-token NAME` replace the current CLI process with Claude through POSIX `execve`; no intermediate shell evaluates arguments. The exceptions start Claude as a child instead: a Console profile's `run` (and `launch-bound … run`), see [Console credit](#console-credit), and `profile login NAME --console` on an API-key profile, see [Console-login profiles](#console-login-profiles). They retain the invoking working directory and terminal. `LaunchCommand.environment` validates supported profiles and clears conflicting credential, provider, model, and nested-session variables before setting the account's literal `CLAUDE_CONFIG_DIR` (or clearing it for the default account). Interactive login happens in Claude Code only after a deliberate action. Discovery never initiates login. Quota monitoring can renew an expired access token through the saved OAuth refresh token.

`claudock usage [--max-age SECONDS | --fresh]` reads quota for supported profiles through the [usage cache](#usage-cache-and-request-pacing) and emits tab-separated window percentages/reset timestamps. A Console profile (API key or Console sign-in) with a credit set gets a row from the credit ledger (plan `Console API`, window `Credit · $X of $Y left`, spent percentage, reset `-`) and no request; without one, and for unresolved profiles, it prints a skip message, which names a Console-login profile's organization. It reports per-account failures, including an unreadable ledger, and returns a failure status when an account has no reading at all; an account that is cooling down or whose request failed prints its cached reading and one stderr note, `claudock: NAME: rate limited until HH:MM; showing reading from N min ago.` or with the failure's reason. No email or credential fields are printed. It performs no automatic polling; the GUI owns scheduled refresh, and both share readings and cooldowns.

## Console API-key profiles

`Profile.authKind` is `subscription`, `apiKey`, `consoleLogin` ([Console-login profiles](#console-login-profiles)), or `endpoint` ([Third-party endpoint profiles](#third-party-endpoint-profiles)); `isConsole` names `apiKey` and `consoleLogin` explicitly, which share Console credit, launching, and display, and `isEndpoint` the last, which takes none of those paths. The registry writes the field only for those two; records without it decode as subscription profiles, so registries without Console profiles keep their bytes. Only managed profiles created through Claudock can have either kind, and registry validation rejects them on any other record. `ProfileStore.setAuthKind` switches a managed Console profile between `apiKey` and `consoleLogin`, keeping its registry ID, name, and config folder; subscription profiles never change kind. A rename keeps the kind and config folder, and so the key's Keychain service. A registry that holds a Console profile is written as version 2 and returns to version 1 when the last one is removed: builds before API-key support accept only version 1, so they refuse such a registry instead of rewriting it without the kind, and builds before Console-login support cannot decode `consoleLogin` and refuse it too.

`ConsoleAPIKey` parses input as data: a trimmed `sk-ant-<type>[0-4 digits]-…` key with a non-empty `[A-Za-z0-9_-]` body and at most 512 characters, or one complete `export ANTHROPIC_API_KEY=…` assignment, optionally quoted. It does not allowlist one key generation: `api03` keys, identity-backed personal keys (`usr`), and types it has never seen are all accepted, because Claude Code sends whatever `ANTHROPIC_API_KEY` holds as `x-api-key` and the Console has introduced key types before. It refuses by whole type segment, before the shape rules, so a long or oddly pasted credential is still named: `oat` and `ort` (subscription OAuth access and refresh tokens) and `admin` (Admin keys) get specific errors because they cannot be used as `ANTHROPIC_API_KEY`, and `sid`, `si`, `cc`, and `ccsr` (Claude session credentials) report that they are not Console API keys. `stored(_:)`, which validates the Keychain item on every read, applies the same rule. No error message, description, or reflection includes the key. The CLI reads keys only from standard input: at a terminal it prompts on stderr with echo off and restores the terminal on every exit, including signals, discarding anything typed or pasted after the first line; otherwise it reads up to 4 KiB to end of input. A key is never accepted as an argument, and a profile-name argument that looks like a Claude key or token is rejected without being echoed.

`APIKeyStore` keeps each key in the generic-password item `Claudock-apikey-<SHA-256 hex of CredentialStore.serviceName(for:)>`, separate from Claude's OAuth credentials and `Claudock-inference-…` tokens. Writes use the same `security -i` stdin path as inference tokens, with the key hex-encoded and a bounded command, then read the item back and compare it. A missing item reads as no key; a locked or unreadable item is an error. Status checks use an attribute-only lookup and never read the key. `ProfileStore.addAPIKeyProfile` saves the key after preparing the registry entry and its account folder but before validating and publishing them; if saving or publishing fails, the registry stays unwritten, the folder is rolled back, and a Keychain item created by that attempt is deleted, while an item that existed before is kept. Removal keeps the item, like other credentials.

`ClaudockCLI.launch`, which serves `run`, managed shortcuts, and the app's Terminal launches through `launch-bound`, starts from `LaunchCommand.environment` (which clears every inherited authentication and provider variable), sets `ANTHROPIC_API_KEY` from Keychain, and keeps `CLAUDE_CONFIG_DIR`. It never sets `CLAUDE_CODE_OAUTH_TOKEN`, and a missing key fails before Claude starts. `SubscriptionConfiguration.validate` still applies: the profile's settings cannot select external providers, override credentials, or point `ANTHROPIC_BASE_URL` away from api.anthropic.com. A plain sign-in is refused for these profiles (`profile login NAME --console` switches one to a Console sign-in instead), and inference tokens are refused for them in `MintTokenStore`.

The monitor reads neither `CredentialStore` nor `UsageClient` for Console profiles, only `APICreditStore.status` (and, for Console-login profiles, the organization). They are shown without limit bars, with a Credit meter once a credit is set, are not errors, do not count toward the updated-profile count, count toward attention only when their credit is low (below 10% or $5 left), and sort after subscription accounts when sorting by usage. Claude Code asks once, in interactive mode, whether to use a custom `ANTHROPIC_API_KEY` and stores the answer in the profile's config folder; Claudock does not pre-answer it.

## Console-login profiles

Claude Code can sign in to an Anthropic Console account itself: `claude auth login --console` creates an API key for the account (`claude auth status --json` then reports `authMethod: api_key`, `apiKeySource: "/login managed key"`, and `orgName`). Claude Code 2.1.295 keeps that key in the login Keychain as the generic-password item `Claude Code` plus the config folder suffix its OAuth credentials use: nothing for a launch without `CLAUDE_CONFIG_DIR` (the default profile), otherwise `-` and the first 8 hex digits of the SHA-256 of the NFC config path, for account `$USER`. On macOS it writes only that item, through `security -i`, failing rather than falling back to a file when the write fails; it reads the item first and a legacy `primaryApiKey` in `.claude.json` only after. It also lists the key as approved in `.claude.json` (`customApiKeyResponses`) and records the account there (`oauthAccount.organizationName`, `billingType`).

`ConsoleLogin.keychainService` derives the same service from `CredentialStore.serviceSuffix`. `ConsoleLogin.isSignedIn` runs `security find-generic-password -a NSUserName() -s SERVICE` without `-w`, so it reads attributes, never the key: status 0 is signed in, 44 is not, anything else is a Keychain error rather than "signed out". Only managed Console profiles reach it. A profile signed in only through a legacy `primaryApiKey` therefore counts as not signed in. `ConsoleLogin.organizationName` reads `oauthAccount.organizationName` from the profile's `.claude.json` (at most 10 MiB) as untrusted text: control and format characters, bidirectional overrides among them, and line breaks become spaces, white space collapses, and the name is cut to 80 characters. The app shows it with `Text(verbatim:)` or plain `String` initializers, never as Markdown, and the CLI passes it through the same control-character filter as every field.

`profile add NAME --console [--directory ABS_PATH]` adds a managed `consoleLogin` profile (no Keychain item is saved first) and then hands over to `claude auth login --console` through the sign-in path of `launch`: the isolated environment with nothing injected, `execve`, and no inference-token requirement. A failed or cancelled sign-in leaves the profile. `profile login NAME` and the app's **Sign in…** (`launch-bound … login`) run the same sign-in for `consoleLogin` profiles; `profile login NAME --console` is refused for subscription profiles.

On an `apiKey` profile, `profile login NAME --console` runs the sign-in as a supervised child through `APICreditLaunch.supervise`, which shares `run`'s spawn, signal forwarding, and job control but starts no receiver. Only when the child exits 0 and `ConsoleLogin.isSignedIn` then finds the item does `ProfileStore.setAuthKind(.consoleLogin)` switch the profile; otherwise it keeps its kind and its key is still injected. Claudock's own key item stays in Keychain, unused, and the CLI prints its service name and delete command. `profile set-key NAME` on a `consoleLogin` profile reads a key as usual and calls `setAuthKind(.apiKey)`, saving the key in its `beforePublishing` hook, so the registry lists the new kind only after the key is saved; Claude Code's item stays. Because the key in `ANTHROPIC_API_KEY` takes precedence over Claude Code's own (`apiKeySource: ANTHROPIC_API_KEY`), injecting the pasted key is enough.

`InferenceTokenPolicy.launchCredential` returns `.consoleLogin` for these profiles whatever the requirement and the arguments, `setup-token` included; sign-in still returns `.profileLogin`. `ClaudockCLI.launch` then checks `ConsoleLogin.isSignedIn` and fails before Claude starts with `NAME is not signed in to a Console account. Sign in with: claudock profile login NAME`; otherwise it hands the isolated environment, with no `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN`, to `APICreditLaunch.run`, so credit is counted exactly as for API-key profiles. Inference-token commands refuse these profiles. Manage profiles shows a Console-login row's sign-in from the same attribute lookup, again whenever the app becomes active because the sign-in finishes in Terminal and the browser, with **Sign in…** and **Set credit…** and no token buttons; the monitor's refresh does no Keychain lookup for it.

## Third-party endpoint profiles

An `endpoint` profile runs Claude Code against a third-party service that speaks the Anthropic Messages protocol, with one model pinned. It is always managed (registry validation rejects the kind on any other record), always gets a new account folder, and stores `endpoint: {"baseURL": …, "model": …}`; the object is required for this kind and rejected on every other. `EndpointConfiguration` validates both as data. The base URL must be `https` with a non-empty host, printable ASCII without white space, no user name or password (no `@` before the path), no `?` or `#` at all, and a port from 1 to 65535 when given; the scheme and host are lower-cased and trailing slashes dropped, and a stored value must already be in that form. The model is one `[A-Za-z0-9._:/-]+` id with an optional `[1m]` suffix, at most 128 bytes. A registry that holds an endpoint profile is written as version 3, one with a Console profile as version 2, otherwise 1, and reading accepts all three. Builds that accept only versions 1 and 2 (1.7.0 and older) therefore report it as invalid instead of rewriting it without the endpoint, and could not decode the `endpoint` kind anyway. `ProfileStore.setEndpoint` replaces the endpoint of a current endpoint profile, keeping its registry ID, name, folder, and key; a rename keeps the endpoint. Endpoint profiles never switch kind.

`EndpointAPIKey` parses input as data: the trimmed input, or the value of exactly one `export NAME=value` or `NAME=value` line (`NAME` a shell identifier, so text after its first `=` is the value), with one pair of matching quotes removed. The value must be 1 to 512 printable ASCII characters without white space and without a quote at either end; any value that starts with `sk-ant-`, in any letter case, is refused with its own error, because the provider would receive it. No error, description, or reflection includes the key. The CLI reads it with the same terminal and pipe rules as Console keys, never from arguments. `EndpointKeyStore` keeps it in the generic-password item `Claudock-endpointkey-<SHA-256 hex of CredentialStore.serviceName(for:)>`, written with the same `security -i` hex command (accepting only that namespace) and read back to verify; status checks are attribute-only lookups. `ProfileStore.addEndpointProfile` saves it before publishing the entry and rolls back the entry, the folder, and an item it created, exactly as `addAPIKeyProfile` does.

`ClaudockCLI.launch` first checks the Claude arguments with `EndpointLaunch.checkModelArguments`: `--model X`, `--fallback-model X[,Y…]`, `--advisor X`, and their `=` forms are refused (exit 2, nothing read or started) unless every model they name is the pinned one. All arguments are checked, after a `--` too, because Claude Code (Commander) takes the argument after an option that needs a value as that value even when it is `--`, so `--append-system-prompt -- --model X` would still select X. `InferenceTokenPolicy.launchCredential` returns `.endpointKey` for these profiles whatever the requirement and the arguments. After `LaunchCommand.environment` has cleared inherited credentials, providers, and models, `EndpointLaunch.environment` removes `OTEL_*` and `CLAUDE_CODE_ENABLE_TELEMETRY`, then sets `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN` (the key; `ANTHROPIC_API_KEY` would make an interactive Claude Code ask to approve a custom key), the pinned model in `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU,FABLE}_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL`, and `CLAUDE_CODE_SUBAGENT_MODEL`, and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` and `DISABLE_NON_ESSENTIAL_MODEL_CALLS=1` (which Claude Code 2.1.296 does not read), and, unless the model ends in `[1m]`, `CLAUDE_CODE_DISABLE_1M_CONTEXT=1`, so the default model (the Opus default plus `[1m]`) stays the plain pinned id. `CLAUDE_CONFIG_DIR` stays the profile's folder.

`EndpointLaunch.arguments` then puts one `--settings` JSON object first in Claude Code's arguments. In 2.1.296 a `--settings` value that is trimmed text in braces is JSON (anything else a file path), it is never written to disk, and when the option is given twice the last wins silently. Flag settings rank above user, project, and local settings and below managed ones, and each source's `env` is copied over the process environment in that order. The object holds `availableModels: [model without [1m]]` (honored from flag settings; `/model` refuses another model, the picker hides it, and a `--model` that slips past is replaced by the default), an `env` that repeats every non-secret endpoint variable plus empty `ANTHROPIC_API_KEY` and `ANTHROPIC_CUSTOM_HEADERS` (so no lower settings file can redirect the host or model, and a settings file's Anthropic key is not sent as `x-api-key` beside the bearer token) and empty `ANTHROPIC_DEFAULT_MODEL`, `CLAUDE_CODE_AUTO_MODE_MODEL`, `CLAUDE_CODE_BG_CLASSIFIER_MODEL`, `CLAUDE_CODE_WORKFLOW_SUBAGENT_MODEL`, `ANTHROPIC_CUSTOM_MODEL_OPTION…`, and `CLAUDE_CODE_USE_GATEWAY` (which the launch also removes from the process environment), `apiKeyHelper: ""` (a project's helper's output would otherwise go out as `x-api-key`), and, with `behavesAs`, `modelPicker: {replaceBuiltInOptions: true, options: [{model, label, description, behavesAs}]}`; `behavesAs` must be a full catalog id (`claude-…`), is looked up by model id so it applies to `ANTHROPIC_MODEL` too, and makes Claude Code take that model's prompt, limits, and context window and stop warning about an unknown model. The key is never in it. A user's own `--settings`, found where Claude Code's parser (Commander) would read it, is read the same way (inline JSON, or a file of at most 1 MiB from the working directory), merged, and removed; settings that choose another model, endpoint, or credential (`model`, `availableModels`, `fallbackModel`, `advisorModel`, `modelOverrides`, `modelPicker`, `apiKeyHelper`, or a pinned, credential, provider, or model variable in `env`) are refused with exit 2, as are an unreadable value and a repeated option. Lists of `availableModels` from several sources are joined in 2.1.296, so a project's settings can still widen the list; only managed settings replace it. `/model` writes the choice made with Enter to `$CLAUDE_CONFIG_DIR/settings.json`, which is the shared settings for a managed profile.

`EndpointSession.check` then refuses (exit 2, unless `run` was given `--allow-cross-provider-resume` before `--`) to resume a session in which a model other than the pinned one replied, because a long Claude-made session can fail on the endpoint during compaction. It reads the arguments with Claude Code 2.1.296's option table and Commander's rules (`ClaudeCommandLine`), and resolves the session as that version does: the folder is `projects/` under the profile's config folder, named by `CLAUDE_CODE_PROJECT_DIR_NAME` when valid, else by the working directory's `realpath(3)` in NFC with every UTF-16 unit outside `[A-Za-z0-9]` as `-` (over 200 units: the first 200, `-`, and the base-36 Java string hash of the path). `--continue` (which wins over `--resume`) takes the session-ID-named `.jsonl` files there, plus `.session-aliases` folders and an older layout's folders, newest modification time first, and passes over what Claude Code passes over: metadata-only files, sidechains and team members, daemon workers, a session that continues in another, one held by a live background process, one recorded for a colliding directory, and, interactively, sessions made with `-p` or `/loop`. `--resume ID` takes the first copy in the folder that holds messages, else every copy in all project folders (Claude Code takes the only one, or prefers its own git worktree); a `.jsonl` path is read as given (interactively only an absolute one); other text matches a session title. Only `type`, `message.model`, and `requestedModel` of entries are decoded, in the transcript and its `subagents` transcripts and their fork parents; an `assistant` entry is the pinned model's when either model, without `[1m]`, is the pinned id without `[1m]` (DeepSeek answers a `[1m]` request as `deepseek-flash`, and Claude Code records that), and `<synthetic>` is Claude Code's own. The picker, remote sessions, and `--from-pr` cannot be resolved first and get a warning; a session Claude Code would not find is left to it. The launch is a plain `execve`: no credit ledger and no OpenTelemetry receiver, since Claude Code prices models it does not know wrongly. `SubscriptionConfiguration.validate` still applies to the profile's own settings, so they cannot set another base URL or a credential.

`usage` prints no row for an endpoint profile and one stderr note, `NAME: third-party endpoint (HOST, MODEL), billed per token by the provider; no quota to read.`, without changing the exit status; `available` skips it with the same note, and `AccountAvailability.classify` returns `.untracked`. `set-credit` (`APICreditError.endpointProfile`), the inference-token commands, and sign-in (`profile login`, `launch-bound … login`) refuse it with one line. The app reads nothing for it during a refresh, shows `Third-party endpoint · HOST · MODEL` without meters, groups it under **Third-party endpoints**, and offers **Replace key…** and **Remove…** in Manage profiles from an attribute-only key lookup; adding one is CLI only, and the add sheet's caption says so.

## Console credit

Anthropic exposes no API for a Console organization's remaining prepaid credit (the Admin Usage & Cost API needs an Admin key and an organization), so the user records it: `claudock profile set-credit NAME AMOUNT` or the app's Set credit… sheet, which share `APICreditAmount.parse` (0 to 1,000,000 US dollars, at most two decimals). `APICreditStore` keeps `~/Library/Application Support/Claudock/api-credit.json`: version 1, per registry ID `{balanceUSD, asOf, requests, adjustments}`, 0600, replaced atomically with fsync under the exclusive `.api-credit-lock` (reads share it). Setting a credit records `asOf` (milliseconds) and drops earlier entries; every write prunes entries from before `asOf`, and requests before `asOf` are not recorded. Money is summed as decimals of each double's shortest form, so 0.0123 + 1.5 + 0.25 is exactly 1.7623; displays round half up to cents. An unreadable ledger is an error for status and recording; setting a credit moves it aside as `api-credit.unreadable-<UTC>.json` and starts a new one.

`ClaudockCLI.launch` hands a Console launch, after the usual environment isolation and the key lookup or sign-in check, to `APICreditLaunch.run`. It starts `APICreditReceiver` on `127.0.0.1` at an ephemeral port and a random `/<128-bit token>/v1/logs` path, then `posix_spawn`s Claude in the same process group with the same terminal, argv, working directory, and inherited descriptors (Claudock's sockets are close-on-exec), the prepared environment plus `APICreditCapture.environment`: every inherited `OTEL_*` and `CLAUDE_CODE_ENABLE_TELEMETRY` removed, then `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_LOGS_EXPORTER=otlp`, `OTEL_EXPORTER_OTLP_PROTOCOL` and `OTEL_EXPORTER_OTLP_LOGS_PROTOCOL` `http/json`, the endpoint, and `OTEL_LOGS_EXPORT_INTERVAL=1000`. Metrics and traces get no exporter. Before spawning it names any settings file (the profile's, the working directory's `.claude/`, or managed settings) whose `env` sets one of those keys, because Claude Code applies settings `env` over the process environment. The child gets default dispositions for the signals the parent changes and an empty signal mask (the calling thread may be a dispatch worker that blocks signals). While it runs, the parent ignores SIGINT, SIGQUIT, SIGTSTP, SIGTTIN, SIGTTOU, and SIGPIPE, forwards SIGTERM and SIGHUP (one that arrives before the child exists is delivered right after), and waits with `WUNTRACED`: when the child stops, as Claude Code does on Ctrl-Z in raw mode, the parent stops itself with the same signal so the shell sees the job stopped, and `fg` continues both. It stops only between ledger writes, so the ledger lock is never held while the job is suspended, and once continued it continues the child too, in case only the parent was signalled. Signals the caller ignored stay ignored by both, and without job control (SIGTSTP ignored) the parent never stops; an ignored SIGCHLD is reset so the child's status is not reaped away. SIGINT or SIGQUIT sent to the parent's process ID alone is not passed on (the terminal signals the whole group, and forwarding a group-wide one would deliver it twice); SIGTERM is. It exits with the child's status, or 128 + the signal that ended it. Subscription launches keep `execve`.

The receiver answers only POSTs of `application/json` to its path without `Origin` or `Sec-Fetch-Mode` headers, so another local process or a web page cannot add spend; HTTP/1.1 with keep-alive, Content-Length or chunked bodies, and `Expect: 100-continue`. Bodies above 4 MiB are read and dropped, above 64 MiB refused; a new connection has 5 s to present its head and a body 30 s; at most 16 connections, evicting the oldest silent untrusted one. Every accepted export is answered 200 after its body is queued, never waiting for the ledger. A serial queue parses `claude_code.api_request` records (`APICreditEvents`) and appends them under the lock as they arrive; after a failed write, batches queue up for five seconds before the next attempt, and a last one runs at exit. Only structural problems (decoding, validation, a symlink, the wrong owner or type, the size) make the ledger unreadable; a failure to open or read it (descriptors, I/O, permissions) is a transient error and never sets the file aside. A request's identity is the SHA-256 of `session.id`, `event.sequence`, `event.timestamp` (or `timeUnixNano`), `request_id`, and `client_request_id`, so a resent batch adds nothing. Its cost is `cost_usd` as a double (or `cost_usd_micros` when absent); records without a session, a time, or a valid non-negative cost are ignored.

When the child exits, the receiver drains, and `APICreditStore.reconcile` reads the profile's `.claude.json`. Claude Code writes `projects[<git root or directory>]` at a graceful interactive exit with `lastCost`, `lastStartTime`, and `lastSessionId`; `-p` runs write none, and `--resume` restores the session's earlier cost and start time. An entry counts only when its `lastStartTime` falls inside this launch and after `asOf`, its `lastDuration` (cumulative on resume) is not longer than the launch, and its session is one this launch captured (or, when it captured nothing, the only entry that started within 10 s of the launch). If `lastCost` exceeds the captured requests of that session since its start, the difference is recorded as a `session-total` adjustment keyed by session and start, replaced on a re-check, never negative.

Probe evidence, Claude Code 2.1.295: per-run `cost_usd` sums equal `total_cost_usd` (also with a subagent) and a fresh interactive session's `lastCost`; settings `env` overrides process OTEL variables; `DISABLE_TELEMETRY` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` do not stop the log export; a SIGKILL loses only requests finished since the last export, while SIGTERM flushes; with these settings no destination besides the loopback endpoint is added. Accuracy limits: use of the key outside Claudock-started Claude Code is not seen; a killed Claude Code loses up to one export interval; if `claudock` itself dies (for example SIGKILL), Claude keeps running and the rest of that session is not counted; an overriding settings `env` or a stopped exporter loses events that the `.claude.json` check recovers only for a graceful interactive exit. The Console balance is authoritative.

## Usage cache and request pacing

`UsageCache` keeps `~/Library/Application Support/Claudock/usage-cache.json`: version 1, per subscription profile keyed by `CredentialStore.serviceName(for:)`, the last successful reading (`plan`, `windows` with their reset times, `fetchedAt`, and the extra-usage fields), `retryAt`, and `rateLimits`, the number of HTTP 429s in a row. It holds no tokens, emails, or account IDs. Writes replace it atomically (0600, a fsync'd temporary file renamed over it) while holding the fetch lock; reads take no lock. A file that is missing, a symbolic link, owned by someone else, larger than 1 MiB, malformed, or of another version reads as empty and the next write replaces it; entries with impossible values or unexpected keys are dropped. Every write drops readings older than seven days, cooldowns that ended more than a day ago, and all but the 256 most recently used profiles, and keeps the file under 1 MiB. A cache that cannot be written is ignored: readings are still shown.

`UsageFetcher` runs one pass: one `claudock usage` or one app refresh. A cached reading is current when it was fetched after the pass started less its max age: 180 s for the CLI by default, `--max-age`, or 0 with `--fresh`; half the refresh interval for an automatic app refresh, and 0 for a manual one. Measuring from the start of the pass lets a reading that another process saves while this one waits count even with max age 0. A profile whose `retryAt` has not passed is not requested, whatever the max age. Any other profile needs a request: the pass takes `.usage-cache-lock`, beside the cache, with `flock`, waiting at most 30 s once per pass and rereading the cache meanwhile, so readings the lock holder saves are used as they land. A pass that cannot get the lock in time requests nothing more and shows cached readings (`MonitorError.usageBusy`). Holding the lock, it rereads the cache, waits until 500 ms after the end of the last request recorded in the lock file, makes the request, records when it ended, and saves the result. Only the lock holder writes that time, so a lost or unwritable cache does not lose it. The pass keeps the lock until it finishes, so concurrent `claudock usage` runs make at most one request per stale profile between them. If the lock file cannot be opened, the pass requests without coordination rather than never.

HTTP 429 sets `retryAt` from `Retry-After` (`UsageClient.retryDate`, kept between five minutes and a day) or, without a usable header, 60 s doubling with each 429 in a row up to 30 minutes, plus up to a quarter more at random so profiles limited together do not retry together. A success clears the cooldown and the count. Other failures keep the cached reading and set no cooldown. In the app, the retry after a rejected token's renewal (HTTP 401) also waits 500 ms from the rejected request, and a 429 from the token endpoint during a renewal is reported as a failed renewal, not as a usage cooldown: the refresher keeps its own cooldown for it.

`UsageRow` holds what a dashboard row shows for a subscription profile. Before a refresh requests anything it merges `UsageCache.entries`, which covers only resolved subscription profiles (an unresolved, Vertex, or Console profile can share a credential service with one) and leaves out readings dated more than a minute ahead: a newer reading replaces the one shown and clears its error, and a later cooldown holds the row as rate limited. A profile still cooling down is not requested; its row still refreshes its email and, when missing, its plan. A current result replaces the reading whatever its date, so a reading taken with a clock that was ahead cannot hold back new ones; an older cached reading never replaces a newer one the row shows.

The usage endpoint is a constant. Only a build compiled with `-D CLAUDOCK_TEST_USAGE_ENDPOINT`, which `Tests/CLIIntegration/usage_e2e.py` makes in its own scratch directory and deletes after the run, reads the endpoint from `CLAUDOCK_TEST_USAGE_ENDPOINT`, and only an `http://127.0.0.1` URL; without one its endpoint has a scheme no request can be sent to. Release and ordinary debug builds contain no override, so no environment can redirect their access tokens.

## Limits and external dependencies

The internal Anthropic usage endpoint is a compatibility boundary, not a supported public API contract. Unknown or invalid response shapes must produce a clear error instead of fabricated zero usage. A last-known reading must be identifiable as stale. Vertex AI billing does not map to Claude subscription allowances.

The zsh reader is a constrained static parser, not a complete shell interpreter. It follows literal includes with size/depth/count bounds, keeps quoted constructs opaque, and skips sensitive-looking paths. It deliberately cannot reconstruct arbitrary dynamically generated configuration. Manual import is the escape hatch.

## Packaging and verification

`scripts/bootstrap.sh` validates the build environment, runs tests, packages into a fresh output directory, and opens the app. `scripts/build-app.sh` builds the current architecture, stages a bundle in the private system temporary directory, generates an AppKit icon, adds the plist, signs the bundled CLI and then the containing app, and verifies both signatures. Staging uses private permissions; public app directories, executable, and resource permissions are normalized before signing so a caller's permissive umask cannot make the app group/world-writable. It refuses to overwrite an existing destination app. Release signing and notarization require the maintainer's own Apple credentials.

Unit tests should use temporary homes and synthetic account responses. App interaction, real Keychain permissions, real Claude authentication, upstream compatibility, signing/notarization, and a packaged launch are distinct checks; a unit-test pass does not establish all of them. CI packages a local-build artifact and does not publish a public release.

Resolved subscription profiles copy an exact Claudock selector through the bundled CLI, including imported profiles. Shell-disabled users receive a quoted absolute CLI path. Only unresolved custom wrappers retain a raw shell command. Registry deduplication uses Claude credential-service identity, while analytics groups resolved history directories; these are separate identities.

## Automatic credential renewal

The resident app attempts one renewal-and-quota-retry cycle on local access-token expiry or quota HTTP 401. HTTP 403, rate limits, offline errors, and server failures do not trigger renewal. The refresh exchange uses the saved scopes and client ID, or Claude Code's public first-party client ID when no custom ID is stored. It sends no model prompt and requests no longer token lifetime.

The implementation follows the directory-lock and JSON formats inspected in Claude Code 2.1.263. It acquires `.oauth_refresh.lock` and the canonical configuration-directory path plus `.lock`, rereads the credential, and adopts another process's updated token when present. The separate `.storage-write.lock` protects short permission-check and read/merge/write/readback operations; it is never held during HTTP. Lock directories stay empty and receive heartbeats. Claudock refuses to steal pre-existing locks, including stale ones; Claude Code can recover its abandoned locks.

Writes target the existing backend, preserve unrelated JSON fields, and retain a returned replacement refresh token. Keychain writes use the same trusted `security -i` stdin path as Claude Code to preserve existing reader access. The app checks the complete document and persistent item identity before and after the write, and refuses a missing item before writing. The underlying `security -U` operation is an upsert, so these cooperative locks and guarded writes are not a transactional guarantee against every external writer: Claude Code has a logout fallback that can bypass its storage lock, and same-user tools can ignore the protocol. An identity mismatch is reported without deleting the other item. File writes use an existing-only atomic swap. A Keychain failure never switches to plaintext.

The Keychain stdin command has a 4,032-byte ceiling. Claudock fails visibly when the encoded document exceeds it; it never falls back to secrets in process arguments. A renewed response that exceeds the ceiling is retained in memory with the other pending-save failures.

Before dispatch, the app durably publishes a private, secret-free `.claudock-refresh-<service-hash>.json` marker in the profile configuration directory. It records only the fingerprint of the submitted token pair. A lost or malformed HTTP response, post-dispatch cancellation, or process crash leaves the marker in place; another process will not resend that same pair. A newer credential clears the old marker. Definitive authentication/rate-limit responses and confirmed saves clear their matching marker. Corrupt markers fail closed.

A successful exchange that cannot be saved stays in memory for a later save attempt, avoiding another POST with the old refresh token. Matching tokens on a changed authoritative backend can receive the pending result while retaining that backend's other fields. Exiting the app loses an unsaved result; the durable marker prevents blind reuse and directs the user to Claude Code or re-login. Credential contention/save failures back off for a minute; an explicit invalid grant is not retried while the token pair remains unchanged. Cancellation before dispatch is not cached. No token or raw OAuth error body belongs in diagnostics.

The one-shot `claudock usage` command reads quota without rotating credentials. It directs users with an expired token to the resident app or their Claude profile, so exiting the command cannot discard a pending rotation.

## Subscription plans and mint authentication

`TerminalLauncher` calls the bundled CLI so GUI and zsh launches select the same saved inference credential through `InferenceCredential.environmentToken`. The CLI passes it to Claude with `CLAUDE_CODE_OAUTH_TOKEN`.

`SubscriptionPlan` recognizes exact Claude Code metadata mappings for Max 5×/20× and Team Premium; unknown seat mappings remain explicit. Quota percentages are never converted into presumed plan capacity.

Long-lived mint credentials are separate from full-scope refreshable credentials. Browser PKCE authorization requests `user:inference` and a one-year lifetime. The server-reported expiry is stored; normal quota OAuth remains available for background refresh. Minting cannot eliminate the usage API's scope requirement.

## Shell ownership and external providers

Adapter v4 defines no `claude-auto` function. At source time, it removes an older generated function only when its current body matches `_claudock_auto_body`, then forgets that ownership record. This cleanup runs even if the registry emitter fails. Existing aliases/functions/executables and user-modified generated functions keep precedence, including legacy named-profile wrappers. New profiles cannot use the reserved `default` or `auto` names.

Profile discovery classifies explicit Vertex/Bedrock/Foundry selection using the legacy serialized external-provider flag. Registry bootstrap/import excludes those wrappers, and old external-provider registrations become suppressed entries on load. A one-time bounded static rescan reconciles older imported Bedrock/Foundry wrappers that had no external flag, only when command and literal config path still match; explicit imports repeat this reconciliation. Configuration folders and shared histories are preserved.

## Paste-first token setup

`MintTokenView` separates direct token import from browser authorization. Direct import is the default and needs no existing OAuth metadata. Pasted opaque tokens carry manual provenance and optional expiry/identity metadata; browser-created credentials retain verified identity and server-reported expiry. Existing credential records remain readable. `InferenceCredential` accepts an imported token with unknown expiry without claiming it never expires; actual server rejection remains authoritative.

`InferenceTokenPolicy` keeps the optional `requireInferenceToken` setting, off by default, in the shared preferences domain that also holds the Claude executable path, so the app's Settings toggle and `claudock require-token` change the same value. `ClaudockCLI.launch` asks `InferenceTokenPolicy.launchCredential` for every `run` and `launch-bound … run`. With the setting off, behaviour is unchanged: a missing token or an expired browser-created token falls back to the profile's own login, while an expired pasted token or an unreadable one stops the launch. With it on, a missing, expired, or unreadable token fails before `execve`. Sign-in launches and `setup-token`, which creates a token, always use the profile's own login, with the setting on or off and whatever the saved token's state, and Console profiles keep using their key or Console sign-in. With the setting off, `launch` turns `MintTokenError.accountMismatch`, which `MintTokenStore.read` raises when the saved token's recorded account no longer matches the profile's login, and `.accountChanged`, which a save raises for the same state, into guidance that names `profile login` and `profile setup-token`; with it on, the refusal above reports an invalid token instead. The core errors keep their app wording.

`claudock profile set-token NAME [--expires ISO8601_DATE]` reads a token from standard input with the same terminal and pipe rules as API keys, never from arguments, and saves it through `MintTokenStore.importToken`. It refuses Console API-key, Console-login, and unresolved profiles before reading input. `claudock profile tokens` prints `MintTokenStore.status` per profile as `none`, `active`, `expired`, `pasted-unverified`, `n/a`, or `unavailable`, with the expiry, and never token material.

`claudock profile setup-token NAME` runs Claude Code's `setup-token` through the sign-in path of `launch` (`signIn: true`, the same environment isolation as `profile login`), so it never reads the saved token or API key and the requirement does not apply. It takes no other arguments, refuses Console API-key, Console-login, and unresolved profiles, and prints one hint line to stderr just before `execve`. It exists because `run NAME -- setup-token` is exempt only when `setup-token` is exactly the first Claude argument; a wrapper that inserts flags first misses that match, and `run` does not guess past flags.

## Credentials a removed profile leaves

Removal keeps every credential, so the person removing a profile needs them named. `ProfileKeychainItems.items(for:)` lists the five Keychain items a profile can have, from the service functions the launches use: `CredentialStore.serviceName` (Claude Code's OAuth login), `ConsoleLogin.keychainService` (the key Claude Code's Console sign-in keeps; the plain `Claude Code` item for the default profile), `MintTokenStore.serviceName` (a saved inference token), `APIKeyStore.serviceName` (a pasted Console API key), and `EndpointKeyStore.serviceName` (a third-party endpoint's key). It does not depend on `authKind`: a profile that switched between a pasted key and a Console sign-in has both, and an imported folder can hold a login of its own. A profile with no known config folder (unresolved, Vertex, or a relative path) has none, because its names would belong to another account's items. The login's title says that it is shared with anything else that uses the folder: Claude Code keeps it in one item, so the other commands of a person who imported the folder lose it too.

`ProfileKeychainItems.lookup(for:)` runs `security find-generic-password -a $USER -s SERVICE` without `-w` or `-g`, so it reads attributes and never a secret, and nothing prompts for access. Status 0 is an existing item and 44 a missing one. Anything else, such as a locked Keychain or a `security` that fails to run, leaves the item `unchecked`: `profile remove` and the app's notice list it with a note instead of hiding it, because the removed profile can no longer be asked for its names. Each item comes with `ProfileKeychainItems.deleteCommand(service:)`, the service quoted for the shell, then the config folder, quoted the same way so the line can go into `rm -r` (the CLI turns control characters, which a terminal must not receive, into spaces and says so; the app's notice shows the quoted path as it is), then a reminder that keys stay valid until they are revoked: at Anthropic in the Console or on claude.ai, and for an endpoint profile's key at its provider. Claudock only prints these commands.

`MintTokenStore.delete(profile:)` is the one deletion Claudock offers a person, for `claudock profile clear-token NAME` and the token sheet's **Delete token**; the only other is the rollback of a failed profile add, which deletes the API-key item that attempt created (`APIKeyStore.delete`). The sheet offers **Delete token** when the row's status shows a token, one of another account included, or could not be read, since a token that no longer decodes is the one to delete. It refuses profiles that cannot hold a token before asking Keychain, and builds `security delete-generic-password -a $USER -s SERVICE` as an argument vector, with no shell, only for a `Claudock-inference-<64 hex>` service, so no Claude Code item can be named. Status 44 means no token was saved, which the CLI reports with exit status 1. After a reported success, a lookup that still finds the item makes the deletion a failure; one that cannot run does not. It never reads the token, so it also deletes one that belongs to another account or can no longer be decoded. Afterwards `profile tokens` shows `none`, and `InferenceTokenPolicy` treats the profile as having no token: a launch uses the profile's own login, or is refused while the requirement is on.

Builds use a private SwiftPM scratch directory rather than placing its SQLite database in a potentially cloud-synced checkout. CLI integration fixtures also use the system temporary directory.
