# Security

## Report a vulnerability

Use this repository's **Security → Advisories → Report a vulnerability** feature to contact the maintainers privately. If private vulnerability reporting is unavailable, open an issue requesting a private reporting channel without technical details, personal data, or secrets. Do not post credentials, Keychain output, `.credentials.json`, shell startup files, session transcripts, or raw account responses.

Include the affected version or commit, macOS version, a description of the trust boundary, and reproduction steps using synthetic profiles. The project does not promise a response SLA. Fixes target the current source version; there is no separate support commitment for older releases.

## Data and trust boundaries

- OAuth tokens come from the selected profile's Claude Keychain service or its existing credential file. They are used in memory and are not copied into the app's profile registry or the usage cache.
- Access tokens are sent to `https://api.anthropic.com/api/oauth/usage`; refresh tokens are sent only to `https://platform.claude.com/v1/oauth/token` for renewal. Both clients reject redirects and use ephemeral sessions. There is no developer-operated server, telemetry, or analytics service.
- Quota readings (plan, usage percentages, reset times, and when they were read) and rate-limit cooldowns of subscription profiles are kept in `~/Library/Application Support/Claudock/usage-cache.json` (0600, replaced atomically) under each profile's Claude credential service name, shared by the app and `claudock usage`. It holds no tokens, emails, or account IDs, and a damaged, oversized, or symlinked file is ignored rather than trusted. `.usage-cache-lock` beside it lets one process at a time request quota and holds only the time of the last request. Only a test build compiled with `-D CLAUDOCK_TEST_USAGE_ENDPOINT` can send usage requests elsewhere, and only to 127.0.0.1.
- Discovery statically parses a bounded set of zsh files and literal includes. It does not source or execute them. Dynamically constructed wrappers may need a manual import.
- The profile registry and new account directories live under `~/Library/Application Support/Claudock/`. CRUD updates the registry without rewriting `.zshrc`. Optional shell integration writes `~/.config/claudock/init.zsh` and a named loader block in `.zshrc`, with a backup before editing an existing file. Integration v4 creates the namespaced `claudock` function and missing `claude-NAME` shortcuts; it preserves existing user aliases, functions, and executables. Legacy files under `~/.config/claude-usage/` remain unchanged. Treat these files as private local configuration, not shareable diagnostics.
- New profiles use private UUID config directories to keep logins independent. Their projects/history and common settings, plugins, and skills are shared with `~/.claude` through symlinks. These shared files are not isolated by account: edits affect every linked profile, and local history cannot establish which account was billed. Explicit folder imports retain their existing layout without automatic shared-data links.
- Shortcut synchronization runs when the init file is sourced and through zsh `precmd`/`preexec` hooks. The internal `claudock shell profile-names` helper emits validated selectors from the existing registry as data, without discovery, registry writes or locks, credential access, or networking. Shortcuts forward the full selector and literal arguments to the bundled CLI. Removal and rename cleanup only remove generated functions whose bodies still exactly match Claudock's recorded definitions; user-edited functions remain intact.
- App startup upgrades an enabled, unchanged Claudock-owned integration v1–v3 to v4. It leaves integration disabled when it was off, and surfaces upgrade failures in Manage profiles. Existing Terminal sessions must load the new init file once or open a new tab; later profile changes are picked up by the loaded hooks.
- The bundled CLI uses the same registry, profile validation, credential mapping, and provider-environment cleanup as the app. `run`, `profile login`, and `profile setup-token` invoke Claude directly with literal argument vectors in the current directory; they do not evaluate a generated shell string. `usage` reads credentials and queries account quota only when invoked, and only for profiles whose cached reading is older than the requested max age (180 seconds by default) and that are not in a rate-limit cooldown; it does not rotate tokens. It prints no email or credential fields. A Console profile's `run` (API key or Console sign-in) is the exception to direct invocation: `claudock` stays as Claude's parent (same process group, terminal, argv, and directory) to receive Claude Code's per-request cost reports, described below. `profile login NAME --console` on an API-key profile also runs Claude as a child, to switch the profile only after the sign-in finished.
- Local analytics reads main sessions and recognized direct/workflow subagent logs in a bounded background scan to extract usage metadata and project paths. Transcripts and token summaries are not uploaded by the monitor. The local dashboard and read-only `--analytics` diagnostic can still reveal profile names, project names, paths, and work patterns; redact screenshots and diagnostic output before sharing.
- Re-login opens Claude Code in Terminal using a private temporary command file that deletes itself when it runs. The file contains command arguments and local paths, never OAuth credentials. Standard re-login remains with Claude Code; the explicit Mint token action uses the matching authorization-code PKCE flow and a separate Keychain item. Claudock can renew expired access tokens using the same refresh token and saves the rotated pair back to the existing credential store. Keychain writes go through the trusted security utility over stdin, with a strict input-size ceiling and no secret-bearing argv. They use Claude's cooperative locks plus full-document and persistent-item identity checks; they do not provide atomic isolation from arbitrary external writers. macOS can require approval to access Keychain.
- **Continue as…** deliberately launches the selected Claude executable with a saved conversation path under the chosen target profile. Claude Code may then send conversation context to its configured provider as part of its normal operation. This explicit Claude workflow is separate from the monitor's local analytics. The target profile's settings and Claude's normal project/tool permission prompts apply.
- Console API keys are stored only in a separate Keychain item per profile (`Claudock-apikey-<hash>`), never in registry JSON, settings, scripts, logs, command output, or process arguments. The CLI reads them only from standard input: at a terminal, echo is off and input after the first line is discarded; piped input must be a single key. It saves them through the security utility's stdin with readback verification. Status checks look up the item's attributes without reading the key. A launch reads the key and passes it to Claude Code as `ANTHROPIC_API_KEY` in the child environment only; Claudock sends it nowhere itself. Claude Code then uses it with Anthropic's API, billed to the key's Console organization.
- Console-login profiles use Claude Code's own Console sign-in (`claude auth login --console`), whose API key Claude Code keeps in its `Claude Code-<hash>` Keychain item. Claudock only looks up that item's attributes to see whether the profile is signed in; it never reads the key, copies it, or passes it to Claude, and it injects no credential into these launches. The Console organization's name, read from the profile's `.claude.json`, is shown as plain text with control and format characters removed.
- Third-party endpoint keys are stored only in a separate Keychain item per profile (`Claudock-endpointkey-<hash>`), read from standard input under the same rules as Console API keys, saved through the security utility's stdin with readback verification, and never written to registry JSON, settings, scripts, logs, command output, or process arguments. A value that starts with `sk-ant-` is refused, so an Anthropic credential is never handed to a third party. A launch passes the key to Claude Code as `ANTHROPIC_AUTH_TOKEN` in the child environment only, beside `ANTHROPIC_BASE_URL`; Claude Code then sends it, with the session's prompts, files it reads, and tool results, to that endpoint. The endpoint URL must be `https` without credentials, a query, or a fragment. These launches clear inherited credentials as every launch does, drop inherited OpenTelemetry settings, and set Claude Code's nonessential traffic off. Each also passes Claude Code a per-launch `--settings` object, never written to disk and never holding the key, that repeats the endpoint URL and model variables and blanks every other credential, provider, and model variable a launch clears (`ANTHROPIC_API_KEY` and `ANTHROPIC_CUSTOM_HEADERS` among them) and `apiKeyHelper`: those settings outrank user, project, and local settings files, so a repository's settings cannot redirect the key to another host, switch the provider, or add an Anthropic key, or a key its helper prints, to the requests. A project or managed settings file that sets `ANTHROPIC_AUTH_TOKEN`, which would replace the key and which `--settings` cannot pin without putting the key in arguments, stops the launch. A user's own `--settings` that sets the model, endpoint, or a credential is refused. Managed settings still take precedence.
- Console credit: for a Console launch (API key or Console sign-in), `claudock` replaces inherited `OTEL_*` variables and turns on Claude Code's OpenTelemetry log export to a receiver it runs on `127.0.0.1`, at an ephemeral port and a random 128-bit path, for that launch only. The receiver accepts only `application/json` POSTs to that path without browser `Origin`/`Sec-Fetch-Mode` headers, bounds request size, time, and connections, and keeps only each `api_request` event's cost, model, session ID, time, and an identity hash; prompts and responses (which Claude Code sends redacted) and other events are discarded. They go to `~/Library/Application Support/Claudock/api-credit.json` (0600, atomic, file-locked), which never holds keys or prompts. The receiver's sockets are close-on-exec. A local process can still deny it connections or make the estimate low, never raise it or read anything; the Console balance stays authoritative.
- Removing a profile preserves its Claude config directory, conversations, and Keychain entry. This is removal from the monitor, not secure deletion or account revocation.

A private `.claudock-refresh-<service-hash>.json` attempt marker contains only a token-pair fingerprint, never credentials. It prevents reusing a possibly consumed refresh token after a lost response or crash. Automatic renewal belongs to the resident app, not the one-shot usage command.

The app runs with the current user's local permissions and is not sandboxed. Anyone or any process with equivalent access may already be able to read or change local configuration. The monitor does not protect credentials from a compromised Mac, untrusted local binaries, or a malicious shell setup used during an explicit Terminal action.

The service endpoint is undocumented and can change or be withdrawn. A local ad-hoc signature verifies bundle integrity but does not establish the developer identity or notarization status of a downloaded release. Maintainers should sign and notarize public app distributions and verify the artifact after packaging.

## Long-lived tokens

Mint token requests inference-only authorization through Claude's first-party public OAuth client and manual callback using random state and an S256 PKCE verifier. The one-year requested expiry is not treated as a guaranteed lifetime. Mint credentials are stored separately from the refreshable usage credential, never in registry JSON or shell scripts. Native launches read that Keychain item and pass a valid token through `CLAUDE_CODE_OAUTH_TOKEN` in the child environment. A process with the same user's debugging privileges can inspect child memory/environment; this is not isolation from a compromised local account.

## Profile admission and shell v4

Claudock accepts official Claude subscription profiles, and Console API-key, Console-login, and third-party endpoint profiles created through Claudock. Explicit provider wrappers (Vertex, Bedrock, Foundry) are excluded from registry bootstrap/import. Legacy external registrations are retired while preserving configuration folders and shared history; a one-time static rescan reconciles older unmarked imported cloud wrappers only when command and literal config path match. Managed profile identities remain authoritative.

Explicit folder imports, new shared-profile setup, and native launches validate account settings with bounded regular-file reads. External-provider flags, API credential/helper overrides, and external base URLs are rejected without logging their values. The direct HTTPS Anthropic endpoint is allowed. This is supported-configuration validation, not isolation against a malicious local user or arbitrary explicit Claude arguments.

Shell v4 removes a previously generated `claude-auto` function only if its body still matches Claudock’s recorded definition. Existing user aliases/functions/executables and legacy profile wrappers are preserved. Unchanged owned v1–v3 adapters upgrade without changing `.zshrc`; current shells load the new adapter on their next source/restart. Shared session lookup retains Claude's native current-project `--continue` and explicit `--resume` semantics. A running source requires `--fork-session` to avoid sharing its writer identity.

## Existing inference token import

The token dialog defaults to direct paste. Clipboard reads occur only after the user presses Paste; the app never reads the clipboard on startup. The parser accepts a supported raw OAuth token or an exact literal environment assignment, without shell evaluation. Imported tokens use the same bounded, separate Keychain namespace as browser-created tokens, and remain out of scripts, registry JSON, logs, and process arguments.

The CLI's `profile set-token` accepts the same input from standard input only, with echo off at a terminal; a token is never taken from command arguments, and `profile tokens` reports status and expiry without token material.

`profile clear-token` and the token dialog's Delete token remove only the `Claudock-inference-…` item, through an argument vector for `security` that accepts no other service, so Claude Code's own login and key cannot be named. They never read the token. `profile remove` lists a removed profile's remaining Keychain items from attribute-only lookups and prints the commands that delete them without running them; deleting an item does not revoke its key or token at Anthropic or, for an endpoint key, at its provider.

Pasted tokens have manual provenance. Their account identity and expiry cannot be established from an opaque string; unknown expiry is represented explicitly. A cached profile identity, when available at import, is only a local binding and not proof that the token belongs to that account. Browser-created tokens retain their strict account/organization checks. The user assigns an imported token to a profile; use its matching quota login when relying on account-specific limits.
